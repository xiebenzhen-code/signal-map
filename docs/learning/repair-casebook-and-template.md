# Signal Map 修复案例与解释模板

日期：2026-10-04。目的：从真实故障学习工程判断，避免“报告很多，但自己没有理解”。

## 1. 证据与轮次说明

本次只读扫描 `docs/reliability/` 的 54 个 Markdown/JSON 文件，找到 **22 个不同的完整研究 requestId**。这不是全部 E2E 数量：部分记录只保留短 ID，页面检查、离线回放、数据库探针和复测也不一定产生研究 ID。

因此不能据现有材料确认“40 多次真实研究 E2E”或“40 多个独立故障”。用户描述的四十多轮可作为待补的经历清单；每轮应按请求、环境、结果和证据去重。下面是已保存报告支持的案例，不重新消费模型预算复演历史请求。

证据等级：**代码契约**＝当前代码与测试；**历史离线**＝替身/回放；**历史实测**＝当时真实服务或页面；**线上实测**＝公网发布版本。不能把低等级或旧版本证据直接升级为当前线上通过。

## 3. 为何反复 E2E 后仍出错

主要是验证边界不断扩大：函数测试看不到接线问题；API 成功看不到页面状态；本地成功看不到线上环境；一次保存看不到下一轮消费；同一来源的一次成功看不到网络抖动。另有材料、版本和运行进程不一致的问题。

改进方式：固定问题和材料；锁定运行版本；用 requestId 串联；先建立成功条件与失败分类；同一失败不无界重试；离线修补后只用预算内的一次真实路径核验；失败就定位阶段，而不是继续靠报告“封口”。

未来 E2E 记录至少包含：版本、环境、用户/过滤器脱敏标识、原问题、固定 URL、提交与内部模型计数、requestId、阶段、响应状态、候选/证据/知识/今日去向、截图、未验证项。多个阶段各有 PASS 不意味着用户价值 PASS。

## 4. 每次让 AI 写报告，但由你完成理解验收

建议每个独立缺陷写一页；同根因复测追加到原报告。无需每条错误堆栈都单独写长文。未来任务的可复制要求：

> 修复前先给出可复现现象与根因假设，明确直接证据和推断；编写有意义的反例并观察红，再做最小修改。修复后用中文说明：为什么这个改动能解决问题，为什么没有选择另外一个合理方案，改动的代价，实际执行的测试与退出码，以及尚未验证的真实链路。保留无关改动，脱敏凭证。最后给我三个基础知识问题，让我用自己的话解释，不替我作答。不能把历史通过、替身通过或 HTTP 200 当作本次用户任务通过。

每页报告按以下模板：

```text
标题 / 日期 / 版本 / 关联 requestId
1. 用户看到什么：原问题、实际行为、期望行为。
2. 失败在哪层：前端 / API / Agent / 来源 / 网络 / DB / 部署。
3. 证据：日志、输入输出、反例；尚未证实的假设。
4. 根因：具体字段、调用或状态为什么产生错误。
5. 最小修复：文件、行为、设计理由、合理备选与代价。
6. 红→绿：失败断言、修补后输出、回归及实际退出码。
7. 真实验收：是否真实用户入口；版本、数据和计数。
8. 未通过项 / 回滚 / 历史数据影响。
9. 学习解释：一个概念、一个图或例子、三个自测题。
```

本次自测：为什么有日期仍可能进不了今日？为什么同一证据重现不应推进修订？为什么一次真实按钮写库不能证明下一轮正确消费？先自己回答，再让 AI 按代码证据纠正。
